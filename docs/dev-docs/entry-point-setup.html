Why this layout

FolderRoleMay import
App/Composition root: app entry, iOS events, dependency wiring, startup stepsEverything (data sources, Firebase, Factory)
Presentation/Views and view modelsDomain, DesignSystem, Support
Support/Small helpers both of the above use (logging)Apple frameworks only
Startup/ lives in App/
Real steps call data sources (Keychain, ModelContainer, UploadKit). Only the composition root may import those (rule §4.2).
StartupViewModel lives in Presentation/
It is the view model of StartupView, so it sits next to it (rule §4.3).
One name: Startup
Startup names the process (steps, sequence, state), its feature folder and its only screen, StartupView. A feature with one screen needs no screen subfolders.
RootView lives in Presentation/Root/
It is a view: it only chooses which screen to show, it wires no dependencies.
Support/ is top level
Both App/ and Presentation/ log; putting it inside one would make the other borrow from it.
Folder = rule
Each top-level folder matches one row of the dependency table, so a CI check can test imports per folder.

Move the existing files

Run order when the app opens

1iOS starts the process; SwiftUI creates SiteLogAppthe @UIApplicationDelegateAdaptor property wrapper creates the AppDelegate instance
2AppDelegate.didFinishLaunchinglogs “App launched”; Firebase goes here later
3SiteLogApp.body → WindowGroup → RootViewstate = .running → shows StartupView (spinner)
4StartupView’s .task calls StartupViewModel.onAppear()
5StartupSequence.run() runs each stepeach step logs ok / failed
6.ready → RootView shows MainTabView · .failed → StartupView shows the error“Try again” goes back to step 5

0project.yml: a single scene

project.yml → targets.SiteLog.settings.base

INFOPLIST_KEY_UIApplicationSupportsMultipleScenes: NO
Why
The app also runs on iPad (TARGETED_DEVICE_FAMILY: "1,2"). iPad can open several windows, and each window is a scene with its own RootView and @State. Startup would then run twice, two windows would compete for the camera, and each window would lock separately.
Then
Close Xcode → xcodegen generate → reopen. Config goes through project.yml, never the Xcode UI.

1SiteLogApp.swift: the starting point

SiteLog/App/SiteLogApp.swift

import SwiftUI

// @main marks where the app starts. Only one type in the app may have it.
@main
struct SiteLogApp: App {

    // Asks SwiftUI to create our AppDelegate and hand it to iOS.
    // We never read this variable; it only keeps the AppDelegate alive.
    @UIApplicationDelegateAdaptor(AppDelegate.self) private var appDelegate

    // `body` describes the app's windows (scenes).
    var body: some Scene {
        // Every window shows RootView as its first screen.
        WindowGroup {
            RootView()
        }
    }

    // No init() on purpose: it runs before AppDelegate's didFinishLaunching.
}
@main
Tells the compiler the app starts here, like void main() in Flutter. There is only one per app.
struct SiteLogApp: App
Conforms to the App protocol, which requires a body.
body: some Scene
A scene is one window of the app.
WindowGroup { RootView() }
A window template: every window that opens shows a new RootView. RootView is the root screen, like runApp(App()).
@UIApplicationDelegateAdaptor
Attaches AppDelegate to the SwiftUI app. Without this line, AppDelegate never runs. You never use the appDelegate variable; it only keeps the instance alive.
No init()
init() runs before didFinishLaunching: Firebase is not configured yet, so a crash there is never recorded.

Inheritance (the superclass). Required because UIApplicationDelegate is an Objective-C protocol.

No other class can inherit from it.

3AppLog.swift: one place for loggers

SiteLog/Support/Logging/AppLog.swift

import os

// A namespace for the app's loggers.
// An enum with no cases cannot be created by mistake: AppLog() does not compile.
enum AppLog {

    // Same subsystem for every logger, so Console can show all SiteLog logs together.
    static let subsystem: String = "app.dd.site.log"

    // One logger per area. Add more later (auth, navigation, ...).
    static let startup = Logger(subsystem: subsystem, category: "startup")
}
os.Logger
Apple’s standard logger: shows in the Debug console (⇧⌘Y) and the Console app, filters by subsystem/category, and has levels (info, error…).
Case-less enum
Cannot be instantiated, so it is only a namespace for constants (the “constants in enums” rule).
No print
print has no levels, cannot be filtered, and prints sensitive data as-is.

4StartupStep + StartupSequence: one step at a time

SiteLog/App/Startup/StartupStep.swift

// Problems that stop the app from starting.
// The UI shows a recovery screen for these.
enum StartupFailure: Error {
    case keychain(String)               // could not read secrets
    case database(String)               // could not open local data
    case unexpected(step: String)       // any other error, with the name of the step that threw it
}

// One thing to do at launch (open the database, read the Keychain, ...).
// Every step is its own type that follows this protocol.
protocol StartupStep {

    // Name used in logs, e.g. "database".
    var name: String { get }

    // true  = if this step fails, the app cannot continue.
    // false = if this step fails, log it and keep going.
    var blocksLaunch: Bool { get }

    // The work itself. `async` = may wait; `throws` = may fail.
    // Runs on the main thread (app target default), so heavy work
    // must be handed to an actor in a package, not done here.
    func run() async throws
}

SiteLog/App/Startup/StartupSequence.swift

// Runs every startup step in order.
struct StartupSequence {

    let steps: [any StartupStep]

    // Returns nil when the app can continue,
    // or the failure that stopped it.
    func run() async -> StartupFailure? {
        for step in steps {
            do {
                try await step.run()
                AppLog.startup.info("Step ok: \(step.name, privacy: .public)")
            } catch {
                // `error` is created by Swift inside every catch block.
                // Log the step name and the error's type, not its full text:
                // the text can contain file paths or other private data.
                let errorType = String(describing: type(of: error))
                AppLog.startup.error("Step failed: \(step.name, privacy: .public), error: \(errorType, privacy: .public)")

                // A non-blocking step only gets logged; the loop moves on.
                if step.blocksLaunch == false {
                    continue
                }

                // A blocking step stops startup here.
                let failure: StartupFailure = makeFailure(from: error, stepName: step.name)
                return failure
            }
        }

        // Every step finished (or only non-blocking steps failed).
        return nil
    }

    // Turns any error into a StartupFailure the UI understands.
    private func makeFailure(from error: Error, stepName: String) -> StartupFailure {
        // The step already threw a StartupFailure: use it as it is.
        if let startupFailure = error as? StartupFailure {
            return startupFailure
        }

        // Any other error (system, SwiftData, ...): wrap it.
        return .unexpected(step: stepName)
    }
}
Why separate steps
The spec says each step is guarded and logged on its own. With one try around everything, a minor failure (a file sweep) blocks the whole app and the log does not say which step broke.
protocol StartupStep
Each step (Keychain, Database, Reconcile…) is a struct that conforms. Adding a step never changes StartupSequence.
blocksLaunch
true: on failure, stop and show the error screen (Keychain, Database). false: log it and keep going.
No Sendable here
The app target sets SWIFT_DEFAULT_ACTOR_ISOLATION: MainActor, so these types are main-actor isolated and already safe to share; Sendable adds nothing. The catch: run() executes on the main thread, so a step must hand heavy work (migration, file sweep) to an actor in a package, never do it inline.
StartupFailure
Only launch-blocking failures reach the user; each case can get its own recovery screen. unexpected catches errors that are not a StartupFailure, so a Keychain error is never mislabelled as a database one.
do/catch inside the loop
Each step has its own try/catch. continue skips to the next step for a non-blocking failure; return stops everything for a blocking one.
makeFailure(from:stepName:)
error as? StartupFailure tries to read the error as our own type. If that works, use it; otherwise wrap it in .unexpected. A separate function keeps the loop short and readable.
type(of: error)
Replaced by type(of: error): logs only the error’s type (e.g. SwiftDataError). The full text can hold file paths or tokens, which spec 07.4 forbids in logs.
privacy: .public
The logger hides interpolated values as <private> by default. Step names and error types are not sensitive, so they are made public.

5StartupViewModel: startup state

SiteLog/Presentation/Access/Startup/StartupViewModel.swift · type viewvm, Name = Startup, then edit

import Observation

// Holds the startup state for RootView.
// @MainActor: state changes happen on the main thread (UI requirement).
// @Observable: when `state` changes, any view reading it redraws.
@MainActor
@Observable
final class StartupViewModel {

    // The only three situations startup can be in.
    enum State {
        case running                    // steps are running, show the spinner
        case ready                      // all good, show the app
        case failed(StartupFailure)     // a blocking step failed, show the error screen
    }

    // private(set): views can read it, only this class can change it.
    private(set) var state: State = .running

    // Not UI state, so SwiftUI does not need to watch it.
    @ObservationIgnored private let sequence: StartupSequence

    // The default value lets RootView write StartupViewModel().
    // Tests pass their own sequence with fake steps.
    init(sequence: StartupSequence = StartupSequence(steps: [])) {
        self.sequence = sequence
    }

    // Called when StartupView appears, and again on "Try again".
    func onAppear() async {
        state = .running

        let failure: StartupFailure? = await sequence.run()

        if let failure {
            state = .failed(failure)
        } else {
            state = .ready
        }
    }
}
@MainActor
State always changes on the main thread; UI can only be updated from main.
@Observable
SwiftUI tracks state automatically; when it changes, RootView redraws. Like emit() in a Cubit.
enum State
Exactly 3 states, so there is no half-way state.
private(set)
The view can read it; only the view model can change it.
@ObservationIgnored
sequence is not UI state, so it is not tracked.
init with a default
No Factory yet, so the dependency comes through init, and tests pass a fake sequence. Once Factory is in, switch to @Injected.
state = .running first
On “Try again”, the spinner shows again while the steps re-run.

6StartupView + MainTabView: view snippet

SiteLog/Presentation/Access/Startup/StartupView.swift

import SwiftUI
import Inject

// The one screen of the startup process.
// Shows a spinner while steps run, or an error with "Try again" if one fails.
struct StartupView: View {
    @ObserveInjection var inject

    // Owned by RootView and passed in, because RootView also reads its state.
    // A plain `let` is enough: @Observable makes SwiftUI redraw on changes.
    let viewModel: StartupViewModel

    var body: some View {
        // Group lets .task and .enableInjection() apply to every branch.
        Group {
            switch viewModel.state {

            case .running:
                VStack(spacing: 16) {
                    Image(systemName: "hammer")      // replace with the app mark later
                        .font(.largeTitle)
                    ProgressView()
                }

            case .failed:
                VStack(spacing: 16) {
                    Text("Couldn't start SiteLog")
                        .font(.headline)

                    Button("Try again") {
                        // A button action is not async, so start a Task to await.
                        Task {
                            await viewModel.onAppear()
                        }
                    }
                    .buttonStyle(.borderedProminent)
                }

            case .ready:
                // RootView shows MainTabView instead, so this never appears.
                EmptyView()
            }
        }
        // Runs once when the screen appears. "Try again" re-runs by itself.
        .task {
            await viewModel.onAppear()
        }
        .enableInjection()
    }
}
One screen, two states
The startup process only ever shows “starting” or “failed”, so one view switches between them. One screen means no screen subfolders: StartupView and StartupViewModel sit together in Access/Startup/.
let viewModel
RootView owns the view model (it needs state to pick the screen) and passes it down. The child does not use @State; that would create a second copy.
.task on the screen
Starts the steps when the screen first appears and cancels them if it disappears. It does not re-run when the state switches to .failed, because it is still the same screen.
Task { } in the button
A button action is synchronous, so it starts a Task to call the async function.
case .ready: EmptyView()
switch must cover every case. RootView never shows this view when ready, so an empty view is enough.
User-facing strings
Hard-coded for now; move them to Localizable.xcstrings when the screens become real.

import SwiftUI
import Inject

// The first screen. Shows the startup screen until the app is ready.
struct RootView: View {
    @ObserveInjection var inject

    // @State keeps the same view model alive while SwiftUI
    // recreates this struct again and again.
    @State private var startup = StartupViewModel()

    var body: some View {
        Group {
            switch startup.state {

            case .ready:
                // M3: replace with AppGateView (lock / sign in / main tabs).
                MainTabView()

            case .running, .failed:
                // Both "still starting" and "failed" are handled by StartupView.
                StartupView(viewModel: startup)
            }
        }
        .enableInjection()
    }
}
@State private var startup
RootView owns the view model; @State keeps it from being recreated every time SwiftUI rebuilds the struct.
Two branches only
Ready → the app. Anything else → StartupView, which handles “starting” and “failed” itself.
case .running, .failed
One case can list several values separated by commas.
@ObserveInjection / .enableInjection()
Hot reload through Inject (see hot-reload.md).
